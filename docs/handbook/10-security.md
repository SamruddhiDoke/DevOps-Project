## 10.1 SonarQube (static analysis + quality gate)

*In general:* SonarQube analyses source code without running it and reports **bugs**, **vulnerabilities**,
**security hotspots** (code needing review), **code smells** (maintainability) and **duplications**, plus test
**coverage** imported from reports. A **quality gate** is a set of pass/fail conditions — by default
("Sonar way") focused on **new code**: no new issues above thresholds, coverage on new code ≥ 80 %, low
duplication, reviewed hotspots.

In this project:

| Item | Implementation |
|---|---|
| Server | SonarQube 26.10 Community, container on the Jenkins host, `127.0.0.1:9000` (Ansible role `sonarqube`) |
| Projects | `order-inventory-backend` (`pom.xml` properties, JaCoCo XML), `order-inventory-frontend` (`sonar-project.properties`, LCOV) |
| Pipeline | stage "Code Quality": Maven Sonar plugin and `sonar-scanner` with `-Dsonar.qualitygate.wait=true` → the step **fails if the gate fails** |
| Token | generated by Ansible into `/etc/jenkins-secrets/sonar_token`, exposed to Jenkins as credential `sonarqube-token` through JCasC |
| Result | quality gate PASSED for backend and frontend (builds #4, #7, #8 — e.g. `QUALITY GATE STATUS: PASSED` in `docs/evidence/jenkins-github-build-7-2026-10-19.txt`) |

Access for humans: `ssh -L 9000:127.0.0.1:9000 ubuntu@<jenkins-ip> -i UniversalKey.pem` → http://localhost:9000
(password in Secrets Manager `order-inventory/sonarqube-admin`).

## 10.2 Trivy (vulnerability, misconfiguration and secret scanning)

| Scan (Jenkinsfile) | What it checks | Gate |
|---|---|---|
| `trivy fs --scanners vuln` on `order-inventory-platform` | **dependency** vulnerabilities from `pom.xml` and `package-lock.json` (libraries we chose) | CRITICAL → fail |
| `trivy config` on the repository | **infrastructure misconfiguration** in Terraform (evaluated with `full.tfvars`), Helm/Kubernetes YAML, Dockerfiles (e.g. public endpoints, root containers, missing encryption) | HIGH/CRITICAL → fail, except the 5 documented IDs in `.trivyignore.yaml` |
| `trivy fs --scanners secret` | **secrets** (keys, tokens, passwords) in the working tree | any → fail |
| `trivy image` per image | **image** vulnerabilities in OS packages (Alpine) and application libraries inside the built image | fixable HIGH/CRITICAL → fail (`--ignore-unfixed`) |

Difference: dependency scanning looks at what the code declares; image scanning looks at everything that
actually ends up in the container (base OS packages, JRE, the built JAR); misconfiguration scanning looks at how
infrastructure is configured, not at software versions.

History: before remediation the images had 11 (backend) and 68 (frontend) HIGH/CRITICAL findings, including a
Spring Framework issue fixed only in Spring 7 → solved by upgrading to Spring Boot 4.1 (Spring 7), nginx 1.30,
patched Tomcat/Jackson versions (`pom.xml` overrides) and `apk upgrade` in both Dockerfiles. Current: 0
findings in both images and dependencies (`docs/TESTING.md`). **Scope of that statement:** "0 known
vulnerabilities in the scanned packages with the vulnerability database of that day" — not "vulnerability-free":
new CVEs appear daily, Trivy does not test application logic, and unfixed CVEs are not gated.

### Accepted findings (`.trivyignore.yaml`) and how false positives are handled

| ID | Finding | Why accepted | Mitigation |
|---|---|---|---|
| AVD-AWS-0040 | EKS public endpoint enabled | admin `kubectl` without VPN/bastion | allow-list = admin /32 |
| AVD-AWS-0041 | public endpoint CIDR | same | `0.0.0.0/0` rejected by variable validation and precondition |
| AVD-AWS-0104 | unrestricted egress (Jenkins, EKS SG) | package installs, ECR, GitHub, AWS APIs | ingress restricted |
| AVD-AWS-0132 | CI bucket uses SSE-S3 not a CMK | reproducible build reports | private, TLS-only, versioned, 30-day expiry |
| KSV-0118 (**only** `k8s/logging/elk.yaml`) | container runs as root (Filebeat) | must read root-owned node log files | read-only root fs, read-only host mounts, all capabilities dropped except `DAC_READ_SEARCH`; all other pods non-root |

Process: every exception is reviewed, justified in writing (statement field + `docs/SECURITY.md`), and scoped
as narrowly as possible (KSV-0118 is path-scoped so a new root container elsewhere still fails the build).
Build #3 shows the gate catching real issues: the first ELK manifest had 5 HIGH findings; 4 were fixed by
hardening, 1 accepted with a path scope.

## 10.3 gitleaks and `.gitleaksignore`

gitleaks scans Git history for secrets. It was run manually before each commit during the remediation and on
a fresh clone after the history rewrite (clean). `.gitleaksignore` lists **two fingerprints** (commit + file +
rule + line) of reviewed false positives: SonarQube's documented factory default `admin:admin` in an old
version of `ci/start-local-ci.sh`. Limitations: an ignore entry silences that exact finding forever, so it
must be reviewed; fingerprints are tied to a commit, so the same text in a new commit is reported again;
gitleaks is not part of the Jenkins pipeline (Trivy's secret scanner is).

## 10.7 Container and workload security

Non-root users (backend UID 10001, nginx UID 101, Elasticsearch/Kibana UID 1000), `runAsNonRoot`, seccomp
`RuntimeDefault`, `allowPrivilegeEscalation: false`, all Linux capabilities dropped, read-only root filesystem
for the backend and ELK, `apk upgrade` at build, pinned base images, immutable tags, Trivy gate, ECR scan on
push, IMDSv2 required on Jenkins (blocks SSRF-style credential theft through IMDSv1).

Application: input validation, generic error messages (no stack traces/SQL to clients — tested), request ids
validated against log injection, no emails in logs, configurable CORS. **No authentication** (documented
limitation).

## 10.8 Historical secret removal and Git history

What happened (`docs/SECURITY.md`): early commits of the public repository contained the RDS master password
(hard-coded in `terraform/main.tf`) and Terraform state files containing it.

- **Why deleting it in a later commit is not enough:** Git stores every version of every file. Anyone can
  check out the old commit (or browse it on GitHub) and read the password. History must be rewritten.
- **What was done:** password removed from configuration (now generated); state files untracked and ignored;
  full backups; history rewritten with `git filter-repo` (state files, `node_modules/`, build output removed
  from every commit; the literal replaced in all blobs), rehearsed on a disposable clone; verified locally
  (0 occurrences, gitleaks clean); pushed on 2026-10-19 with the owner's explicit approval using
  `git push --force-with-lease=main:9857ca7 origin main` (the lease makes the push fail if the remote had
  changed unexpectedly); verified on a fresh clone (32 commits, 0 occurrences, gitleaks clean).
- **Why the credential still had to be treated as compromised:** it was public for some time; clones, forks,
  caches and search indexes may keep it; GitHub still serves the old, unreferenced commits by SHA until its
  garbage collection or a Support purge. The protection is that the database it belonged to was **destroyed**
  and the password **never reused** — a new 32-character generated password protects the new instance.
  Rewriting history reduces exposure; **rotation** is what actually removes the risk.
- Open item (**BLOCKED** on GitHub Support): request a purge of cached views of the old commits (e.g. `8fbc012`).

## 10.11 Viva questions

| Question | Answer |
|---|---|
| Why is deleting a password from the latest commit insufficient? | Git keeps all history; the old commit still contains it. Rewrite history **and** rotate the credential. |
| Why rotate even after rewriting history? | Copies may exist outside your control (clones, forks, caches); only rotation (or, here, destroying the database) makes the leaked value useless. |
| What does Trivy scan and how does a finding stop the pipeline? | Dependencies, IaC configuration, secrets, images; the gate commands use `--exit-code 1`, so a finding makes the shell step fail and Jenkins stops the build. |
| How do you handle false positives? | Review, justify, scope narrowly (`.trivyignore.yaml` statements, path scopes; `.gitleaksignore` fingerprints), document in `SECURITY.md`. |
| Does 0 findings mean secure? | No; it means no known (fixable, for the gate) issues in scanned components at scan time. |
| Why IMDSv2? | Requires a session token obtained with a PUT request, which blocks most SSRF attacks from stealing instance-role credentials. |
| What would you add for production security? | HTTPS, authentication/authorisation, WAF, least-privilege DB user, secrets via External Secrets Operator, GuardDuty/Security Hub, image signing, MFA everywhere, root key removal. |
