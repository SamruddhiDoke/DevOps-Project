# Part 18 — Presentation and explanation scripts

[← Handbook](../COMPLETE_PROJECT_HANDBOOK_AND_VIVA_GUIDE.md)

Simple spoken English. Every claim below is implemented and verified (evidence in `docs/TESTING.md` and
`docs/evidence/`). Do not memorise word for word; keep the order of ideas.

## 1. 30-second introduction

"My project is an order and inventory management system — customers, products and orders — but the focus is
the DevOps platform around it. Every change I push to GitHub is tested, checked for quality and security,
packaged into containers and deployed to Kubernetes on AWS with zero downtime, and it rolls back by itself if
the new version is unhealthy. All the AWS infrastructure is written in Terraform, the build server is configured
with Ansible, and I measured zero failed requests across releases and failures."

## 2. One-minute introduction

"The application has a React frontend, a Spring Boot REST backend and a MySQL database. The interesting
business rule is stock: when two customers try to buy the last item at the same time, only one may succeed —
I solve that with database row locks inside a transaction and I have a concurrency test that proves it.

Around it I built the delivery platform. Jenkins watches the GitHub repository, runs 29 backend and 21 frontend
tests, a SonarQube quality gate and Trivy security scans, builds two Docker images with an immutable tag made
of build number and commit, pushes them to Amazon ECR and deploys them to Amazon EKS with Helm. The rollout adds
a new pod before removing an old one, waits for health checks, and rolls back automatically on failure.
Terraform created the VPC, EKS, RDS, ECR, IAM, encryption keys, monitoring and the Jenkins server; Ansible
configured Jenkins and SonarQube. CloudWatch alarms notify through SNS, and logs go to an ELK stack where I can
trace any request by its id. Finally, to control cost, one script suspends the whole environment and another
restores and verifies it in about ten minutes."

## 3. Three-minute technical explanation

1. **Application (30 s).** "Spring Boot service with layered design — controllers, services, repositories. Flyway
   owns the schema; Hibernate only validates it. Orders lock product rows in ascending id order, check and
   deduct stock in one transaction; cancelling restores stock exactly once. Errors are mapped centrally: 400,
   404, 409 for conflicts, 503 when the database is down — never stack traces."
2. **Health model (20 s).** "Liveness does not check the database; readiness does. So during a database outage
   the pods leave the load balancer but are not restarted."
3. **Pipeline (50 s).** "Checkout and tag, environment check, backend tests with coverage, frontend lint/tests/
   build, SonarQube quality gate, Trivy for dependencies, infrastructure code and secrets, Helm lint, Docker
   build, Trivy image gate, then — only if everything passed — ECR push, Helm deploy with automatic rollback,
   verification that the right image runs, an in-cluster readiness check and a smoke test through the public
   load balancer."
4. **Infrastructure (40 s).** "Three subnet tiers in two availability zones: public for the ALB, NAT and
   Jenkins; private for the EKS nodes; isolated database subnets with no internet route for RDS. State is in an
   encrypted, versioned S3 bucket with locking. Jenkins has no stored AWS keys — it uses an instance role — and
   it may only edit one Kubernetes namespace."
5. **Operations (40 s).** "Thirteen CloudWatch alarms to SNS with verified delivery to an SQS audit queue, a
   budget alert, ELK with request-id tracing, and the suspend/resume scripts with a recovery manifest."

## 4. Five-minute architecture explanation (follow diagram 1 and 2 in [13-diagrams.md](13-diagrams.md))

- "Start at the user: the browser connects on port 80 to an Application Load Balancer in the two public
  subnets. The load balancer is not in Terraform — Kubernetes creates it from my Ingress through the AWS Load
  Balancer Controller. It sends `/api` to the backend pods and everything else to the frontend pods, directly to
  the pod IPs."
- "The pods run on two t3.medium worker nodes in private subnets, one per availability zone. They have no public
  IPs; to pull images from ECR and reach AWS APIs they go out through the NAT gateway."
- "The backend connects to RDS MySQL 8.4 in database subnets that have no route to the internet. The RDS
  security group only allows the EKS cluster's security group, and the connection must use TLS. Credentials are
  generated by Terraform into Secrets Manager and copied into a Kubernetes Secret that is encrypted with my
  KMS key."
- "Jenkins runs on its own EC2 instance in a public subnet but only my IP can reach it. It talks to the cluster
  through the private API endpoint and has edit rights only in the application namespace."
- "Monitoring: CloudWatch watches RDS, Jenkins, the nodes, the NAT gateway and the load balancer; alarms go to
  an encrypted SNS topic; logs go to Elasticsearch in the cluster through Filebeat."
- "Everything except the load balancer is created by Terraform from code; the state lives in S3. Jenkins
  software is installed by Ansible."
- "For cost, the environment is suspended between demos: nodes to zero, load balancer removed, Jenkins and RDS
  stopped, everything else kept."

## 6. CI/CD pipeline — detailed explanation

"The pipeline is the `Jenkinsfile` in the repository, so it is versioned with the code. Jenkins polls GitHub
every five minutes; a new commit starts a build. The tag is build number plus short commit. First I run the
cheap, fast checks: tool versions, backend tests with coverage — a build with zero tests fails on purpose —
then frontend lint, tests and build. Then SonarQube analyses both and the build waits for the quality gate.
Then Trivy: critical dependency CVEs, high or critical misconfigurations in Terraform, Helm and Dockerfiles —
with five reviewed exceptions — and secrets. Helm lint renders the chart. Only then do I build images, and Trivy
scans them; fixable high or critical vulnerabilities stop the build. If all gates pass, Jenkins logs in to ECR
with its instance role, pushes both images, configures kubectl and calls my deploy script. The script records the
last good Helm revision, runs `helm upgrade --wait`, and rolls back if the pods do not become ready. After that
the pipeline verifies that both deployments run exactly this tag, checks readiness inside the cluster and runs
a smoke test through the public load balancer. If anything fails after the deploy, the failure handler rolls
back to the recorded revision. Reports are archived in Jenkins and in S3."

## 7. Zero-downtime deployment — detailed explanation

"Zero downtime needs several pieces working together. One: the rolling update has `maxUnavailable` zero and
`maxSurge` one, so Kubernetes first starts one new pod and only removes an old pod after the new one is ready.
Two: readiness checks the database, so a pod only receives traffic when it can really serve requests. Three: when
an old pod is stopped, it first sleeps ten seconds in a preStop hook, because removing it from the load balancer
takes a moment; then Spring Boot shuts down gracefully and finishes requests in flight. Four: the load balancer
has a twenty-second deregistration delay. Five: PodDisruptionBudgets keep at least one pod during node
maintenance. And if a new version never becomes ready, the old pods were never removed, so users see nothing
and the script rolls back. I proved it on AWS with continuous traffic: 9,532 requests during two releases, a
broken image, a release that could not reach the database and a restart — zero errors."

## 8. AWS architecture — detailed explanation

Use §4 above plus: "IAM is least privilege: my deployer user is a PowerUser with IAM rights only for resources
named `order-inventory`; Jenkins can push to two repositories, describe one cluster and write to one bucket; the
load balancer controller and the EBS driver use IRSA roles bound to single service accounts. Encryption: KMS for
Kubernetes secrets and alerts, encrypted RDS and EBS, encrypted S3 with TLS-only policies. Network: three tiers,
security groups referencing each other instead of IP ranges, administrator access limited to one IP address."

## 9. Security and cost optimisation explanation

"Security: no secrets in Git — passwords are generated by Terraform into Secrets Manager; an old password had
leaked in the public history, so I rewrote the history, verified it on a fresh clone, and the database that
used it had already been destroyed, so the value is useless. Containers run as non-root with read-only file
systems and no Linux capabilities. Trivy and SonarQube gates run on every build. The database is private and
TLS-only; Jenkins and the Kubernetes API accept only my IP.

Cost: small instance types, ECR lifecycle and S3 expiry rules, log retention limits, a budget alarm, and the
suspend script: from roughly 311 dollars a month running to roughly 126 a month suspended, by my estimate from
list prices. The remaining cost is mostly the EKS control plane and the NAT gateway, which I keep so that
restore is reliable."

## 10. Honest limitations and future improvements

"Things I would change for real production: HTTPS with a certificate — it is HTTP only now; real
authentication — the login page is only a demo; Multi-AZ RDS with deletion protection and final snapshots; a
dedicated least-privilege database user instead of the master user; autoscaling for pods and nodes; a webhook or
GitHub Actions with OIDC instead of polling; managed logging instead of a single-node Elasticsearch; canary or
blue-green releases; and removing the last owner-side items: deactivating the root access key and enabling MFA
for all human users."
